## Failure cases (retrofitted 2026-08-12)

1. **Save gates proactively client-side** (like Customer Types, unlike Suppliers) — red icon on
   `Name*` visible on page load, Save disabled until filled.
2. **CRITICAL — the create cascade is NOT atomic, and a failed duplicate-name attempt orphans a
   real address record.** Tested: fill Add form with a real existing client name (`----`) + a
   fresh address, Save. `POST /wm/addresses` fires first and **succeeds** (`201`, real address
   created) — only *then* does `POST /wm/clients` fire and fail with **`422 Unprocessable Entity`,
   "Record already exists."** The address from the failed attempt is left behind as a genuine
   orphan record; it does not get rolled back. Found and deleted it manually via
   `GET /wm/addresses?query=[{"column":"addressName","operator":"EQ","value":"<name>"}]` then a
   direct `DELETE /wm/addresses/{id}`.
   **This is a materially different failure mode than Suppliers**, whose equivalent duplicate-key
   test returns a clean `409 Conflict` with **zero orphan address** (the supplier-uniqueness check
   apparently runs before the address step there). Never assume a cascade's atomicity/ordering
   from one screen carries over to a sibling screen — each has to be tested on its own failure
   path, not just its happy path.
   **Practical implication for an executor:** any automated retry-on-failure logic for this
   specific screen's Add form must account for a partially-applied first attempt — a naive retry
   after a 422 will accumulate orphan addresses, one per failed attempt, unless it explicitly
   cleans up first.

## Correction — cascade order and the unverifiable delete (2026-08-13)

The create order above was wrong in this file and in `KNOWLEDGE-BASE.md` §3b: `packingConfigurations`
fires **before** `clientWarehouse`, per the recorded sequence in `../../http/flows/clients.json`.

That also undermines the "delete in exact reverse order — verified" claim. `POST /wm/packingConfigurations`
returns **201 with a completely empty body** — no `resourceId`, no fields — and the created row is
not retrievable from the collection listing either, so **there is no id to address it by**. Its
delete path is therefore unverified, and `../../http/exchanges/packingConfigurations.jsonl` has no
`read-created`, no `delete-valid` and no `confirm-gone`. Treat the reverse-order delete as an
untested assumption, not a verified procedure.
