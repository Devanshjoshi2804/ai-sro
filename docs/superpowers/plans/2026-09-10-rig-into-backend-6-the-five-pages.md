# The Five Pages Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rebuild the rig's operator console as five pages in the Next.js console, reading the ported backend routes, so `new_agent_arch/src/rig/web/index.html` can be deleted in phase 7.

**Architecture:** Five routes under `frontend/src/app/(dashboard)/`, each a three-line server component delegating to one client component in a new `frontend/src/features/workflow/` feature. All I/O goes through `frontend/src/lib/api/client.ts` and TanStack Query. Every string the operator reads and every number formatting rule lives in one pure module, `features/workflow/format.ts`, so it can be tested against hostile input with no server — the property the rig's `spendLine` comment demanded and the only part of the old page that was ever unit-testable.

**Tech Stack:** Next.js 16 app router (server component pages, `"use client"` feature components), TanStack Query v5, Vitest 4 + jsdom + Testing Library, Tailwind v4, shadcn `base-nova` on `@base-ui/react`, `lucide` icons.

**Spec:** `docs/superpowers/specs/2026-09-07-the-rig-into-the-backend-design.md` — section *The console*, and *Sequence* item 6.

**The dollar and count formats, which differ on purpose:**

| Where | Format |
|---|---|

**Three differences from the rig that every task must respect:**

1. **The paths changed.** The rig called `/v1/runs`; the backend serves `/v1/workflow-runs`, because `/v1/runs` already means a *skill* run here. Never call `/v1/runs` from this feature.
2. **The write routes take no body.** `POST /v1/workflow-runs/{id}/approve` and `.../abort` are bare POSTs — the rig sent `{}` and `{device_id}`; a body here is at best ignored and the route is documented as answering a bare tap. `POST /v1/workflow-runs` takes `StartWorkflowRunRequest` with **`workflow_id` and `device_id` required** and `values`, `live` (default `false`), `allow_focus` (default `true`), `from_step` (default `0`) optional. **There is no `started_by` field** — the rig sent `started_by: "form"` and the backend derives the starter from the credential instead.
3. **`GET /v1/devices` has one shape, not two.** The rig's single route answered a `registered` key of objects to the Browsers strip and a `devices` key of id strings to the run form. Here it is `{devices: DeviceLineModel[]}` for both readers.

- `SpendResponse` is `{cost_usd, unpriced, cap_usd}`. The rig's header line rendered nineteen fields. - `WorkflowHistoryModel` is `{total, held, stale, earned}`. The rig's `became()` also read `last`, `offers` and `counsel`. Those are not served by `/v1/workflows`. Render the four that exist.

## Rulings made before execution

These resolve questions the spec left open. They are decided; implement them as written.

1. **Route group is `(dashboard)`,** not `(console)`. `(console)` is deliberately chromeless because the thread console owns the viewport; these five pages want the nav bar.
2. **Spend is both a page and a header line.** In the rig, spend, needs and browsers were visible on *every* view — the needs strip was an orange alarm box you could not navigate away from. Five separate pages lose that. So `/spend` exists as a page, and a compact spend line also sits in the dashboard top bar, exactly where the rig kept it.
3. **A workflow run's detail is its own route, `/jobs/runs/[id]`,** not a panel inside a card. This keeps it alive when the workflow it came from vanishes from the list — the case the rig's `carryOver` could not handle — and it keeps the workflow-run id space visibly apart from the skill-run id space that `/runs/[id]` already owns.
4. **Restore is on the Browsers page.** The rig had no un-revoke; the backend grew `POST /v1/devices/{id}/restore` in phase 4a. A revoked row gets a `restore` button where a live row gets `revoke`.
5. **The gestures view and the models/bake-off view are out of scope.** The rig's landing view read `/v1/streams` and `/v1/gestures`; its bake-off view read `/v1/bakeoff` and `/v1/bakeoff/readings`. None of those four routes were ported and the spec names five pages, not seven. Task 8 records this in writing so phase 7 deletes them knowingly rather than by omission.

```ts
/**
 * Every string an operator reads off these five pages, and nothing else.
 *
 * Pure on purpose, which is the one property the rig's own page argued for:
 * "A pure function so it can be run against hostile and awkward input rather
 * than only ever existing inside a fetch." Nothing here fetches, and nothing
 * here touches React.
 */

/** A run, a step, or anything else carrying a bill. */
export function money(thing: { cost_usd: number; unpriced: boolean }): string {
  // Three states and not two. A call billed on a model missing from the price
  // table records $0.0000 with `unpriced` set; drawing that as $0.0000 is a
  // bill the page invented.
  return thing.unpriced ? "unpriced" : `$${thing.cost_usd.toFixed(4)}`;
}

/** One line of what has become of a mined job. */
export function became(runs: {
  total: number;
  held: number;
  stale: number;
  earned: boolean;
}): string {
  if (!runs.total) return "never run";
  const parts = [`${runs.total} run${runs.total === 1 ? "" : "s"}`, `${runs.held} held`];
  if (runs.earned) parts.push("writes unasked");
  if (runs.stale) parts.push(`${runs.stale} step${runs.stale === 1 ? "" : "s"} matched weakly`);
  return parts.join(" · ");
}

/**
 * The day against its cap.
 *
 * `overCap` is separate from the text because it drives a colour, and because
 * an unpriced day is over the cap however small its total reads: a day whose
 * cost cannot be established is not a cheap day.
 */
export function spendLine(s: {
  cost_usd: number;
  unpriced: number;
  cap_usd: number;
}): { text: string; overCap: boolean } {
  // A negative cap is how this deployment says "no cap"; `>= cap` would then
  // be true for every day and paint a green deployment permanently red.
  const capped = s.cap_usd >= 0;
  const overCap = capped && (s.unpriced > 0 || s.cost_usd >= s.cap_usd);
  const head = capped
    ? `$${s.cost_usd.toFixed(4)} of $${s.cap_usd.toFixed(2)} today`
    : `$${s.cost_usd.toFixed(4)} spent today`;
  // Omitted at zero rather than written as "0 unpriced": the clause exists to
  // be alarming, and one that is always there is not.
  return { text: s.unpriced ? `${head} · ${s.unpriced} unpriced` : head, overCap };
}

/**
 * A timestamp as the record holds it: the rig's UTC, seconds kept, the `T`
 * spent on a space. Deliberately not localised — this is what the row says.
 */
export function when(t: string | null | undefined): string {
  return String(t ?? "").slice(0, 19).replace("T", " ");
}

/** Midnight today in the reader's OWN zone, shaped for `<input type="datetime-local">`. */
export function startOfToday(now: Date = new Date()): string {
  const pad = (n: number) => String(n).padStart(2, "0");
  return `${now.getFullYear()}-${pad(now.getMonth() + 1)}-${pad(now.getDate())}T00:00`;
}

/** A run's outcome as a card says it: dry runs are marked, live ones are not. */
export function outcomeLabel(run: { outcome: string; live: boolean }): string {
  return run.live ? run.outcome : `${run.outcome} (dry)`;
}

"The two-press revoke and the audit walk in a real browser" → Task 10, and Task 3's disarm test covers the property a browser walk would otherwise be the only witness to.

**Interface consistency.** Every component imports only names Task 1 exports. `startWorkflowRun` returns a `WorkflowRunModel` whose id field is `id`; Task 6 reads `id` and its test asserts that specifically. `approveWorkflowRun` and `abortWorkflowRun` take one argument, the run id, and Tasks 4 and 7 both call them that way.

**Known gap, named rather than hidden.** Tasks 2–7 mock the api module, so no test in this plan proves a request reaches the backend correctly — the same limitation phase 5's extension suites had. Task 10's build, screenshot sweep and live route probes are the only thing standing in for that, and they exercise the read routes only. The write routes — start, approve, abort, revoke, restore — are proven by nothing in this plan, because proving them means driving a real browser at a real warehouse system. That belongs to phase 7's live proof, and it must not be claimed before then.
