## D10: runs stuck at "running" are closed honestly (runtime follow-up from D4/D9)

**Why.** A Steel run's Temporal workflow has `execution_timeout = budget_s + K_BUDGET_MARGIN_S` (`infrastructure/temporal/durable.py` around :96; `K_BUDGET_MARGIN_S = 600` in `domain/execution/progress.py`). The workflow can end without running `finish`: it timed out, the worker died, the workflow was terminated, or the handoff failed. Then the `workflow_runs` row stays `outcome='running'` forever. It holds its broker lease and browser session. It blocks the one-running-run-per-device partial index (`models.py` around :658-664, extension runs). The panel shows it as running.

**Behaviour:**
- **A periodic sweep closes stale rows.** It sits next to the existing sweeps; see `application/connection/keep_open.py` `sweep` and how the worker schedules its periodic jobs. It finds rows with `outcome='running'` whose time is up: `started_at + budget + K_BUDGET_MARGIN_S` has passed, or the durable side reports the workflow closed (ask Temporal through the existing `durable` adapter; add a `describe_run`-style port method only if none exists).
- **How a row is closed:**
  - with a real outcome (`failed`; `timed_out` only if the domain already has it — don't invent outcomes without checking the check constraint and the console);
  - with a plain reason: "the run stopped responding and was closed after its time ran out";
  - `finished_at` is set;
  - the broker lease is released (`application/runtime/broker.py` `release`), and so is the Steel/browser session (`application/connection/browsers.py` `release`), each through the existing code path.
- **Idempotent and race-safe.** Closing uses compare-and-set on `outcome='running'`, so a run whose real `finish` lands at the same moment wins and is never overwritten. Two sweeps at once close a row once.
- **Extension-executor runs:** closed only by the same time rule (no Temporal). Never close a run that is waiting on a question with the operator: a waiting run is not stuck. Find how waiting is represented, and exclude it.
- **The thread that started the run** gets one line saying it was closed and why. It uses the existing run-finished message path, if one exists.

**Tests (invariant 16):**
- A real run row started through `StartWorkflowRun` and left running past its time is closed with its reason, and its lease and session are released.
- A run that finished normally is untouched.
- A run waiting on a question is untouched.
- Racing the real `finish`: `finish` wins, and the sweep does nothing.
- Two sweeps close a row once.
- Postgres integration tests for the compare-and-set and the race (written, not run).

**Out of scope:** the panel's "stopped" wording when finish won the race (design 3). No migration unless a needed column is truly missing; if one is needed, take the next free number after the current head and say so.
